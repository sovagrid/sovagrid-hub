# SovaGrid API v1

The public HTTPS origin is provided by a reverse proxy. The Hub itself listens on `127.0.0.1:8765` over HTTP by default; `serve --bind` changes its IPv4 listen address for a closed Docker bridge network. Do not expose the Hub port directly. All paths below are relative to the HTTPS origin. Request and response bodies are JSON, timestamps are Unix seconds UTC, and all JSON responses use `Cache-Control: no-store`. Request reads time out after 10 seconds. The default JSON body limit is 16 KiB; check configuration allows 32 KiB, while check claim/run/result and Agent enrollment bodies allow 4 KiB. Binary file-transfer limits are documented separately below.

Hub account authentication: `Authorization: Bearer <session token>`. Agent authentication: `Authorization: Bearer <server-specific agent token>`. These token types are separate and never appear in URLs. Password-login Hub sessions expire after eight hours; root SSH grant sessions expire after one hour. Both are bound to one enabled account on this Hub. The Hub stores SHA-256 hashes of random tokens, never the tokens themselves. Clients must keep the returned tokens in secure device storage or only in memory.

Login rate limiting is per source IP: after five failed attempts, that source receives `429` for 30 seconds. Password change separately limits incorrect current-password attempts by both source IP and account session hash, so changing IP or opening another session alone cannot evade the delay. For requests from a trusted reverse proxy, Hub uses `X-SovaGrid-Client-IP` only when Caddy overwrites the header with `{remote_host}` and the proxy address is loopback or explicitly listed with `serve --trusted-proxy`. Other peers cannot set their own source IP through this header.

Each Hub has its own accounts and database. To authorize a client using root/sudo SSH access to **that same server**, run a short-lived copy of its already installed Hub image from the Docker host:

```sh
docker compose --env-file /etc/sovagrid/deploy.env -f /opt/sovagrid-src/sovagrid-blueprint/deploy/compose.yaml run --rm --no-deps -T --entrypoint python3 hub -m sovagrid_hub --db /data/hub.sqlite ssh-grant
```

The Docker command requires host root or equivalent Docker access. The one-shot process runs as the installed Hub's UID `10001` and PID 1, so it can use the same private SQLite volume without creating root-owned WAL files. A child command in the live Hub container is refused. No image build, published port or service restart is needed. The command prints JSON with `protocol:1`, a random `grant`, its `expires_at`, and the selected local administrator `username`. It accepts no grant or password in command-line arguments. The client sends the grant once in the JSON body to the Hub origin it reached over its SSH tunnel or trusted HTTPS connection; clients must not put grants in URLs or store them. Issuance chooses the oldest enabled unrestricted local administrator. The grant is bound to that account's ID and revision, so a password reset, role change, disable or deletion before redemption invalidates it. Redemption inserts a normal role-checked session. Five failed grant redemptions from one source IP cause a 30-second `429`; the JSON body is capped at 128 bytes. The HTTP API cannot mint grants. Hub audit records issuance and redemption metadata, never the grant or session token.

The compatibility response is read-only: it does not ingest a metric, lease a job or change an Agent session. The Hub image receives `SOVAGRID_BUNDLE_MANIFEST_SHA256` from the verified source bundle at build time; a missing or malformed value makes the endpoint return `503`. It reports the digest embedded in the **running image**, so rolling back to an older image also restores that image's digest. An updater for an externally enrolled Agent may require an exact digest match with its candidate before touching an externally enrolled Agent; older Hub images have no endpoint and fail that check. Identical manifests are a conservative same-release check, not a promise of arbitrary cross-version compatibility.

An Agent maintenance lease is an authenticated, per-server **queue gate**, not permission to replace an Agent. Acquisition and Web/Telegram job creation and Agent job dispatch serialize in SQLite write transactions; the Hub also rejects new terminal/file relays while the lease is active. Acquisition requires no queued or delivered job, no unexpired Telegram confirmation, and no relay known as active to the current Hub process. The token is stored only as a hash; it lives for 120 seconds, can be renewed before expiry, and cannot extend beyond 900 seconds from acquisition. Renewal is bound to the running Hub process epoch and bundle digest, so a Hub restart or image change yields `409`; the old gate expires unless the updater has independently recovered. Admin Agent-token rotation returns `409` while the lease is active. Audit events record acquisition, renewal, expiry, and release without the token. Timestamps are UTC Unix seconds.

`agent_idle_proven:false` is intentional. A previously delivered file operation can outlive the Hub's in-memory relay record, and an upload session can remain in the Agent after its Hub request has completed. An external Agent updater must obtain and hold a separate root-only Agent-side quiescence/idle acknowledgement, then keep both that acknowledgement and the Hub lease valid through commit or rollback. This endpoint alone must never authorize a live external Agent update.

### Hub backup control

The optional Blueprint backup broker runs on the **Ubuntu host** as root. Hub reaches only its Unix socket at `/run/sovagrid-hub-backup/control.sock`; the backup directory and Telegram token are never mounted into the Hub container. The broker checks the caller's kernel UID (`10001`) and accepts only bounded snapshot and restore operations. The Hub HTTP routes additionally require an enabled, unrestricted administrator session. No file download, backup deletion, scheduler, or arbitrary broker command is exposed.

`POST /api/v1/backups` can take several minutes. The browser should create and retain one UUID idempotency key for a user action, send `{}` as JSON, and allow a long request timeout. The root broker writes a private key-to-snapshot reservation **before** starting the snapshot. A replay with the same key verifies and returns that snapshot with `200`; after a recoverable pre-publication failure it retries only the reserved snapshot ID. A different key within five minutes receives `429`, and server update/restore lock contention yields `503`. If an HTTP response is lost, the result is uncertain: refresh `GET /api/v1/backups` and verify any new ID before offering a manual retry with the **same** key. Never generate a new key automatically for that retry. The broker validates at least 1 GiB or 5% free-disk headroom in addition to the CLI snapshot limits; low space, partial recovery state, or full snapshot count returns `409`. A missing or unavailable broker returns `503`. All responses are `no-store` and never contain a token, file path, database content, or backup manifest.

`RestoreRecord` has exactly `{ "ok", "protocol": 1, "request_id", "target_id", "phase", "safety_id", "plan_id", "hub_running", "error", "created_at" }`, with UUIDs and UTC Unix seconds. `ok` is true only for `complete`; a valid failed or unfinished record is still returned with HTTP `200` by status, or `200`/`202` by POST. The browser must verify the selected snapshot, show a separate restore confirmation, generate one request UUID, and retain that UUID across a lost response. The root broker validates the target and reserves at least the current database's live and safety copies, the selected target's staged copy, plus 1 GiB or 5% of filesystem capacity **before** stopping Hub. It uses the host update lock and the same durable orchestrator journal as Connect. An identical replay returns the recorded state without another exchange; a different target with the same UUID is refused. The broker continues after its HTTP caller disconnects. The Hub container is stopped and restarted during a real restore, so the HTTP response and active login session may be lost. Sign in again and use the status/history routes; do not automatically issue a new restore request. A pre-dispatch Hub audit row may itself be rolled back with the database. The root-only journal retains request UUID, target UUID, state and time independently.

When the journal says `recovery_required` and Hub remains stopped, its Web API cannot authorize a recovery request. Use Connect over root SSH or the host CLI to inspect the same UUID and explicitly run `recover`. Web recovery is available only while Hub is running. Low disk, ambiguous Compose container, or a conflicting restore returns `409`; broker unavailability returns `503` and the outcome must be checked before a new action.

Agent management is available only after a remote enrollment has received its first metric and its registered credential digest still matches the current server credential. It does not expose a bearer, install software, or change local Agent opt-ins. The administrator-only picker returns at most 256 matching servers ordered by name and ID; `truncated:true` indicates more exist. A per-server read returns revision `0` until the command gate first changes. POST requires a canonical enrollment UUID, lowercase 64-character credential digest, strict boolean `enabled`, and an integer `expected_revision` in `[0,2^63-1]`. A successful actual flag change increments the management revision by one; a no-op preserves it and returns `changed:false`. The original `/commands` route shares this counter. A stale revision, inactive enrollment, or changed enrollment/credential identity returns `409`; an unknown server or remote enrollment returns `404`. Both reads and writes recheck the current administrator session in their transaction. Disabling cancels queued commands and pending Telegram confirmations and closes only that server's terminal/file relays; delivered commands may finish. Audit details contain the enabled flag, revision and whether it changed, without the credential digest.

The password-change route requires a valid Hub bearer session and the correct current password. The new password must contain 12–1024 characters, include a non-whitespace character, and differ from the current password. Incorrect current password returns `403`; after five failures the same source IP or session gets `429` for 30 seconds. A successful change immediately revokes only that account's sessions, closes its in-memory browser terminal/file operations, and cancels its queued web jobs; delivered jobs may finish. Passwords are never placed in URLs, response bodies, or audit details. The bootstrap password file `/etc/sovagrid/admin-password` is not changed by this API and becomes stale after a Web password change.

`HubUser` contains exactly `{ "id": "<UUID>", "username": "…", "role": "viewer|operator|admin", "enabled": true, "revision": 1, "created_at": <Unix seconds>, "updated_at": <Unix seconds> }`. Password hashes, salts, bearer hashes, and passwords are never returned. Usernames are immutable, case-sensitive, unique, and contain 1–80 printable characters without surrounding spaces; up to 1000 accounts may exist. Passwords contain valid Unicode text (including emoji), with the bounds above.

Viewer accounts can read server summaries, metric history, incidents, maintenance windows, monitoring rules, and sanitized VPN inventories. Operators can additionally acknowledge incidents. Administrators can manage accounts and every other API function, including commands, job output, interactive terminals, files, journal requests, monitoring changes, and Telegram. Hub accounts and Telegram bindings are separate identities. All roles can read their own session, change their own password, and log out. Valid sessions with insufficient roles receive `403`; unavailable/expired sessions receive `401`.

### Reviewed external Agent update

These routes are available only to an enabled unrestricted administrator. `GET /api/v1/external-agent-update` returns `{protocol:1,hub_only,current_hub_manifest_sha256,external_agent_manifest_sha256,idle_endpoint_present,live_idle_ack_verified:false}`. It checks only socket metadata; it does not claim a live idle ACK. `POST /api/v1/external-agent-update/preview` and `/preflight` take exactly `{archive_sha256,current_hub_manifest_sha256}` (lowercase 64-digit hex) and return the installed root CLI's bounded metadata JSON. A candidate archive must already be staged on the host by SHA-256. `preflight` returns the exact `review_sha256`, source changes, and pending live gates; it makes no mutation.

`POST /api/v1/external-agent-update/apply` takes exactly `{request_id,archive_sha256,current_hub_manifest_sha256,external_agent_manifest_sha256,review_sha256,confirmed:true}`. `request_id` is a canonical UUID generated by the client **before** POST. The broker durably stores the four digests under that UUID and starts only the installed fixed updater unit, outside the backup broker's read-only `/opt` sandbox. A replay with identical digests returns the existing operation without a second start; changed digests return `409`. Another accepted/running operation returns `409 EXTERNAL_BUSY`. Every POST requires a same-origin browser request when an `Origin` header is present; apply is audited with its UUID and digests. The browser must never submit apply automatically after an uncertain response.

POST apply and `GET /api/v1/external-agent-update/operations/<request_id>` return exactly `{format:1,request_id,phase,created_at,updated_at,error}`. Phases are `accepted`, `running`, `complete`, `failed`, or `uncertain`; times are UTC Unix seconds; `error` is null for the first three phases and an uppercase code otherwise. `GET /api/v1/external-agent-update/operations` returns `{operations:[...]}` with at most 64 recent records and no hashes, paths, or secrets. A lost POST reply can be reconciled through the pre-generated UUID or this list after a page reload. If the one-shot updater is inactive/failed after the accepted grace period or has exceeded its bounded lifetime, status becomes `uncertain/RECOVERY_REQUIRED`; this read never reruns apply. Refusal or an unavailable dedicated unit leaves the source unchanged or requires host recovery according to the operation status. The Hub root socket exposes no arbitrary command, URL, or file path.

### Optional server access policies

Existing users and Telegram bindings have implicit `mode:"all"`, preserving their current role on every server. An unrestricted administrator can switch one principal to `mode:"selected"` with an explicit list of unique server grants. Each grant has `server_id` and `role` (`viewer`, `operator`, or `admin`); the principal's Hub or Telegram role caps it. `viewer` reads that server's summaries, metrics, checks, maintenance and incidents. `operator` also acknowledges its incidents. `admin` also manages its Agent, check configuration, command gate, jobs, VPN/Amnezia actions, journal, terminal and files. Agent-token routes remain scoped to their own server credential. Missing grants deny all access to that server. Lists of servers, incidents, jobs, Agent management and audit events are filtered **before** pagination. Direct server paths and job/incident IDs enforce the same policy. Audit events without a server ID are absent from selected administrators' view.

Only an enabled, global-role `admin` with `mode:"all"` can edit access policies or global users, Telegram bindings, enrollments, monitoring settings and server creation. Selected principals cannot read the Hub-wide `/api/v1/vpn` inventory because it has no server ID; they can still use server-specific VPN actions with an admin grant. The last unrestricted administrator cannot be restricted, disabled, demoted or deleted. A policy edit uses a separate integer `revision` starting at `0`, runs in a SQLite write transaction, and increments it once. A stale revision returns `409`; malformed or repeated grants and unknown servers return `400`; an unknown principal returns `404`; a valid session without authority returns `403`. PATCH accepts up to 1024 grants and a 128 KiB JSON body. `mode:"all"` requires an empty grants list. Reverting to `all` uses the latest revision and restores the global role on every server. Policy edits close that Hub user's active terminal and file relays and cancel its queued web jobs, or cancel the Telegram binding's pending confirmations and queued jobs. Already delivered commands may finish, but their results remain hidden from a principal whose access was revoked. Job leasing, Telegram incident delivery and long polls recheck current access after policy edits.

All account edits use the target account's revision. Every accepted PATCH increments it by exactly one, including a no-op; a permission/status change also revokes that account's sessions. Password reset increments the revision and always revokes that account's sessions. A stale revision, duplicate username, user limit, or an attempt to demote, disable, or delete the last enabled administrator returns `409`; a missing target returns `404`. Guards and revision checks run in one SQLite write transaction. Other accounts' sessions, jobs, and file/terminal operations remain active. Already delivered remote jobs may finish. A user who changes their own role, status, or password must sign in again when sessions are revoked.

On upgrade, the former singleton administrator keeps its existing scrypt password and gains a stable UUID. Its existing sessions are assigned to that account atomically; the old credentials table is removed. If an unusual legacy database has ambiguous session ownership, legacy sessions expire instead of being assigned to an arbitrary account. API effects recheck roles after request-body reads and inside their write transaction. Queued job claims, terminal polling, and file relays check the account's current enabled status and administrator role. Audit events use `hub:<UUID>` and `actor_username`; trusted local CLI actions use `local-cli`.

Monitoring settings are global to the Hub. The CPU, memory, and root-disk thresholds are percentages in `[1,100]`; `offline_seconds` is an integer in `[10,86400]`; `trigger_minutes` is an integer in `[0,1440]`, defaulting to `0` for immediate alerts. Booleans, nonfinite numbers, missing required fields, and extra fields are rejected with `400`. A legacy POST without `trigger_minutes` retains its current value. GET returns revision `0` and the `serve` flag defaults until an administrator first saves settings. A save commits the complete settings and revision atomically to SQLite. A concurrent save using an older revision returns `409`; reload and review the current values before trying again. Ingest uses the new thresholds on the next metric sample; the ten-second offline sweep uses the new timeout without restarting Hub. The server's `online` flag uses `offline_seconds` without the extra alert delay, so the panel can show a server offline while its alert is pending. The audit log records old and new numeric values and never includes a credential. A legacy database gains the new columns and candidate table on `serve`; the first UI save overrides any command-line defaults. Changing these settings cannot detect a Hub machine that itself has gone offline.

When `trigger_minutes` is positive, a resource or failed-service threshold must still be breached by a new Agent report at least that many minutes after the first breach. Pending conditions live in SQLite and do not appear in the incident list until confirmed. A healthy sample clears a candidate; a telemetry gap longer than `offline_seconds` resets resource candidates because it cannot prove continuous pressure. Missing service inventory clears only an unconfirmed service candidate, while an already-firing service incident remains active until a known healthy inventory arrives. For offline alerts, the hold starts one second after `last_seen + offline_seconds`, and the ten-second sweep confirms it. A rule threshold change restarts its unconfirmed hold on the next observation. These choices keep short spikes and momentary disconnects out of incident history.

Optional pressure alert policy has its own revision and does not alter the legacy monitoring settings response. `thresholds` must contain exactly seven keys: `high_psi_cpu_some`, `high_psi_memory_some`, `high_psi_memory_full`, `high_psi_io_some`, `high_psi_io_full`, `high_cpu_iowait`, and `high_cpu_steal`. Each is `null` (off) or a finite percentage in `(0,100]`. The first five compare Linux PSI `avg10`; the last two compare the Agent's CPU iowait/steal percentages. `hold_seconds` is an integer in `[30,86400]`, initially 60. A firing incident requires a second high sample after the hold period. A low sample resolves it. A legacy Agent or a kernel that omits the category cannot confirm or resolve an enabled rule; it clears only its pending hold. A long telemetry gap or a change to a rule/hold also clears the pending hold. Disabling a rule resolves an already-firing incident in the same settings transaction, even if its Agent is offline; an owed recovery enters the durable outbox, while maintenance still suppresses a recovery for an unannounced breach. These incidents use the same maintenance windows, server grants and durable per-chat Telegram outbox as other alerts. The policy is disabled by default; its API is prepared for a future client settings view.

The separate root-inode rule is also disabled by default. `GET/POST /api/v1/monitoring/inode-settings` uses exactly `{ "threshold_percent": null|number, "hold_seconds": 60, "revision": 0 }` with a compare-and-swap revision. It evaluates only the `/` entry in validated `details.filesystems`, and only when `inodes_total > 0`, `0 <= inodes_available <= inodes_total`, and the reported percentage agrees with the fraction of used inodes (within 0.05 percentage points). Hub computes the percentage from the counters rather than trusting the reported value. No root entry, missing detail from an older Agent, unsupported zero inode count, or contradictory data is unknown: it clears an unconfirmed hold but never asserts recovery for a firing incident. A confirmed low sample resolves `high_root_inodes` and follows the normal durable Telegram recovery path. A change to the threshold or hold, including switching the rule off, retires the old incident administratively without a recovery message and drops any queued firing/reminder notifications from the old policy. The next sample begins a fresh hold for an enabled rule. This global rule applies to every enrolled server; only an unrestricted administrator may change it.

Telegram's `mode` is `managed` for the default token beside the database or `managed_externally` when `serve --telegram-token-file` points elsewhere. In external mode, token POST and DELETE return `409`; binding changes still work. A missing managed token leaves the bot off, while an unsafe or invalid stored file yields a secret-free `error`. `connected` becomes true after a recent successful long poll and false when polling stops or fails. `last_success_at` is a nullable Unix timestamp. `pending_incident_notifications` counts durable per-recipient incident messages still waiting for a send or retry. `bot_username` is a nullable public username from the last successful `getMe` verification; it is retained across restarts only when its token digest matches the loaded token. BotFather token plaintext is never echoed by these routes, placed in audit details, or stored in SQLite. A malformed token returns `400`, a rejected token `422`, and unavailable Telegram verification or unsafe storage `503`.

In the normal pairing flow, an unbound user sends `/start` or `/connect` to the bot in a private chat. The bot records a `PairingRequest` with `user_id`, `chat_id`, `first_name`, `last_name`, `username`, and `requested_at` but grants **no commands**. The administrator approves it with a role or rejects it in the panel. `BotBinding` contains the same identity fields plus `role`; names are optional for manually created bindings. The API rejects group chats and any pair where user and private chat IDs differ. Pending requests expire after seven days, at most 100 may exist simultaneously, repeated `/start` does not create another row, and rejection blocks resubmission for 24 hours. Approval and rejection return `404` if the request was already consumed, rejected, or expired. The manual bindings endpoint and `/whoami` remain recovery options. Deleting or demoting an admin binding cancels its pending confirmations and queued commands, as described below.

`ServerSummary` has `id`, `name`, `created_at`, `last_seen` (nullable), `online` (boolean), `access_role` (`viewer`, `operator`, or `admin`), `remote_commands_enabled` (boolean), `maintenance` (nullable active-window summary with `id`, `server_id`, `starts_at`, `ends_at`, `reason`), and `latest` (nullable `Metric`). `access_role` is the current account or Telegram binding role capped by its grant for this server; clients should use it to present available actions, while every API route checks access again. The Hub computes `online` from the last metric receipt and the configured offline timeout (120 seconds by default).

`MaintenanceWindow` has `id`, `server_id`, `starts_at`, `ends_at`, `reason`, nullable `cancelled_at`, and derived `status` (`active`, `ended`, or `cancelled`). `ends_at` must be an integer from one minute to seven days after the Hub's current time. `reason` must have 1–200 printable characters after trimming and at most 512 UTF-8 bytes; control characters, blank text, booleans, and extra fields are rejected. All times use the Hub clock. Windows start immediately; there is no future scheduling. The active window is visible in `ServerSummary.maintenance`, while GET keeps up to 100 historical windows for that server. Creating and cancelling are audited with the server and window IDs; the start audit includes the reason and end time.

During an active window, Hub continues to store metrics, incidents, and incident recovery timestamps; the incident list and `/alerts` remain visible. Telegram alerts for that server are suppressed, including an older alert still pending in the SQLite outbox when the window begins. On expiry, the ten-second sweep sends one firing alert for each incident still active; cancelling early releases these alerts immediately. An incident that first fires during the window and recovers before a reminder produces neither a delayed firing alert nor a misleading recovery message. A previously alerted incident that recovers after the window ends produces a recovery notification, even if its reminder was not needed. An incident already firing when the window starts is included in the post-window reminder if it remains active. This state is transactional in SQLite and survives a Hub restart. Incident notifications are committed to a per-recipient SQLite outbox in the same transaction as the incident transition. A Hub restart, missing bot token, or transient Telegram failure leaves them pending. The sender leases a row for 60 seconds and retries transient failures with exponential backoff capped at one hour. A recovery waits for its firing alert for the same incident and recipient; removing a private-chat binding cancels pending rows. The sender rechecks that binding and maintenance immediately before HTTP. Telegram can accept a message while the HTTP response is lost, so retries can produce duplicates (at-least-once semantics). Permanent invalid or blocked-chat Telegram responses (400/403/410) cancel that row and dependent recovery; token failures (401/404) continue retrying so an administrator can replace the token. Delivered or dropped rows for resolved incidents are pruned after 30 days; pending rows are kept. The outbox contains incident IDs, chat IDs, event type, times, and metric values; it stores no bot token, key, command text, output, or journal content. Legacy active incidents receive delivered markers during the one-time schema migration so their uncertain historical firing message is not replayed.

`Metric` requires `collected_at`, `cpu_percent`, `memory_percent`, `disk_percent`, `network_rx_bytes`, `network_tx_bytes`, `load1`, and `uptime_seconds`. Optional fields: `memory_total_bytes`, `memory_available_bytes`, `disk_total_bytes`, `disk_available_bytes`, and `details`. Percentages are numbers in `[0,100]`; byte counters, load, and uptime are nonnegative. The Hub rejects samples whose `collected_at` differs from its clock by more than five minutes. Network byte counters are cumulative since host/interface reset, not rates. Both `ServerSummary.latest` and each history item include `details` as an object; for old samples or clients it is `{}`.

`details` is an optional, fixed-schema object with only these categories:

| Key | Shape | Meaning |
| --- | --- | --- |
| `swap` | `{total_bytes, free_bytes, used_percent}` | Swap capacity and use |
| `filesystems` | Array of `{mountpoint, fstype, total_bytes, available_bytes, used_percent, inodes_total, inodes_available, inodes_used_percent}` | Mounted filesystem capacity and inode use |
| `interfaces` | Array of `{name, rx_bytes, tx_bytes, rx_errors, tx_errors}` | Per-interface cumulative counters |
| `load5`, `load15` | Nonnegative numbers | Five- and fifteen-minute load |
| `processes` | `{running, blocked}` | Linux process counters |
| `top_processes` | At most 10 `{pid, name, rss_bytes}` objects | Processes with the largest resident memory footprint; available only in an online server's latest summary |
| `disk_io` | Array of `{device, read_bytes, write_bytes}` | Per-device cumulative I/O counters |
| `services` | `{failed_count, units}`; at most 16 `{name, active, sub}` units | Number of failed systemd services and states of failed or watched units |
| `journal_units` | 1–16 unique exact `.service` names | Local read-only journal allowlist advertised by an Agent that opted in |
| `containers` | Versioned UTC snapshot with separate Docker and Podman source states and up to 12 bounded container records per source | Opt-in read-only inventory; CPU/RAM/health/restarts may be null if the Engine cannot supply them |

When `details.services.failed_count` is above zero, Hub opens a `failed_services` incident; zero resolves it. If the Agent cannot obtain the systemd inventory and omits `services`, Hub keeps the previous incident state instead of reporting recovery.

### Digest-based remote Agent enrollment

These admin endpoints support a GUI installer whose Agent credential is generated and saved on the destination server. The provisioning flow sends only its SHA-256 digest to Hub; it does not transfer the plaintext bearer to Connect or return it from this API. At runtime the Agent naturally sends its bearer to Hub in the Authorization header over verified HTTPS. Hub hashes it for comparison and never persists that plaintext token. Existing `POST /servers` and its one-time token response remain compatible.

The enrollment ID and supplied server ID are canonical lowercase UUIDs prepared with the target's durable installation checkpoint. `name` contains 1–80 valid, printable Unicode characters without surrounding whitespace. `agent_token_sha256` is exactly 64 lowercase hexadecimal characters representing a securely generated Agent token. Extra fields, duplicate JSON keys, invalid Unicode/types, query parameters and bodies above 4 KiB are rejected. GET requires no body and returns protocol `1` plus a nullable record, allowing a client to distinguish support from an older Hub's `404` without creating anything.

`AgentEnrollment` contains exactly:

```json
{"id":"8e264f58-9e0c-4be1-8545-1a50457e3ba0","server_id":"514e5d0e-d47f-47a3-966e-680a6718d1f3","name":"Remote server","state":"pending","revision":1,"created_at":1790000000,"last_seen":null}
```

POST atomically creates the server and an immutable request mapping inside one SQLite write transaction after rechecking the current administrator session. A new server has remote commands disabled and no metric history. At most 128 uncompleted enrollments may be pending globally; exceeding that limit returns `409`. Existing ordinary servers and active/cancelled enrollments do not consume a pending slot. The normal offline sweep ignores servers that have never sent metrics, and the Web server list displays them as awaiting Agent.

Repeating the exact request with the same enrollment ID returns the same record with `200`, including when a registration response was lost. JSON field ordering is irrelevant; the supplied server ID, name and digest must match. Another payload for that ID, an occupied/reserved server ID, or an intervening Agent token rotation returns `409` without replacing credentials. Names are not unique identifiers and are never used for deduplication. All current administrators may read/resume/cancel these registrations, including after the creator account is removed; the original creator UUID remains immutable audit metadata. No SSH credential, digest, private key or token is returned by enrollment endpoints or recorded in their audit details.

`state` is `pending` until the first accepted metric fills `last_seen`, then `active`. Active state remains even when metric history is pruned or the Agent goes offline. Enrollment revision remains `1`: metric receipt changes derived connection state, not the immutable request. The metric HTTP route passes its Agent bearer into `Store.ingest`; the credential is checked again in the same write transaction that inserts the sample and updates `last_seen`. Trusted existing local callers may continue omitting the keyword argument; HTTP always supplies its bearer string.

Cancel requires the observed enrollment revision and rechecks authorization transactionally. It deletes only the server created by that mapping, only while `last_seen` is null, and only if its original identity, credential and settings remain intact. Any stored metrics, jobs, confirmations, incidents/candidates, maintenance, saved check configuration or other server-referencing state prevents automatic deletion with `409`, including future foreign-key dependent tables. An empty revision-0 check configuration created by early Agent polling is harmless bookkeeping and can be removed; an administrator's saved configuration, even empty, is protected. A legacy server without an enrollment mapping cannot be cancelled through this API.

Cancellation changes the record to `state:"cancelled"`, revision `2`, and null `last_seen`, preserving a small durable tombstone and its reserved server ID. The same cancellation request with the original revision `1` returns the same `200` record and produces no second audit event; another positive revision returns `409`. Cancel of an unknown ID returns `404`. Re-registering a cancelled ID always returns `409`, so retry cannot silently resurrect the server or credential; a new installation must prepare fresh IDs. Tombstones are not automatically expired in this increment.

Cancellation and first metric use the same SQLite transaction boundary. If cancellation wins, subsequent/inflight old-token metric writes fail `401`; if the first metric wins, cancel fails `409` and preserves the working server. Neither an interrupted GUI nor late cancellation automatically deletes a server that has already connected. This API does not install packages, manage SSH accounts, stop tunnel processes or clean destination files; the separate installer must reconcile those marked artifacts explicitly. Existing Hub/Agent network exposure is unchanged.

### Explicit HTTP, HTTPS, TCP and DNS availability checks

No check or network target exists by default. An administrator saves up to 16 definitions for one enrolled server. Only that server's authenticated Agent receives the targets. Hub does not connect to them or enqueue shell commands. Checks do not require remote-command permission: two dedicated Agent workers probe independently of metric, terminal, file and command polling. Older Agents leave checks waiting; older Hubs return `404`/`405`, causing updated Agents to back off for five minutes without modifying metric payloads.

`CheckDefinition` is a strict tagged union. Common fields: `id` (canonical lowercase UUID), `name` (1–80 valid Unicode characters without surrounding whitespace or controls), `kind` (`http`, `tcp` or `dns`), `enabled` (boolean), `interval_seconds` (integer 60–3600) and `timeout_seconds` (integer 1–10). HTTP adds `url`; HTTPS may also add optional `tls_alert_days` (`null` or integer 1–90) and `ca_cert_der_b64` (`null` or canonical base64 of one X.509 DER CA certificate, at most 1536 decoded bytes). Missing or `null` `tls_alert_days` means certificate expiry alerts are off. A non-null CA must have BasicConstraints `CA=true` and, when KeyUsage exists, `keyCertSign`. TCP adds exactly `host` and integer `port` (1–65535); DNS adds exactly hostname `host`, `record_type` (`A` or `AAAA`) and nullable `expected_ip` of the selected family. DNS with no expected address succeeds when the Agent resolver returns any valid answer of that type. With an expected address, at least one answer must match. DNS uses the Agent's configured operating-system resolver; no custom nameserver or non-A/AAAA record type is supported. Unknown fields, duplicate IDs, invalid Unicode and booleans in integer fields return `400`.

HTTP URLs must use HTTP/HTTPS, fit 1024 UTF-8 bytes and contain no userinfo, query, fragment, backslash, whitespace or controls. DNS names use ASCII labels (IDNs may be supplied in punycode); IP literals include IPv6. IPv6 zone IDs, noncanonical numeric IPv4 aliases, unspecified and multicast addresses are rejected. Private and loopback targets are explicitly permitted: availability is measured from the selected Agent. There is no scanning or automatic discovery.

```json
[
  {"id":"71034824-b083-4298-a091-059d81513c92","name":"Website","kind":"http","enabled":true,"url":"https://example.org/health","tls_alert_days":14,"interval_seconds":60,"timeout_seconds":5},
  {"id":"c6177b0a-9f02-48a7-a0e3-43bfdde0e134","name":"Local SSH","kind":"tcp","enabled":true,"host":"127.0.0.1","port":22,"interval_seconds":60,"timeout_seconds":5},
  {"id":"d17d9b60-f215-4bd0-b47a-b75431b77caf","name":"DNS A","kind":"dns","enabled":true,"host":"example.org","record_type":"A","expected_ip":null,"interval_seconds":60,"timeout_seconds":5}
]
```

Configuration GET initially returns revision `0` and an empty list. The admin-only response includes the configured CA bytes; the viewer/operator summary does not. POST replaces the complete list in one SQLite transaction, rechecks the admin's current session and compares the supplied revision. Every successful save increments revision, including no-op saves; stale revision returns `409`. Every save invalidates all active check leases for that server. A changed target, kind or CA clears that check's history; name, scheduling and enabled changes retain results. Removing a check deletes its history and lease. Audit includes only IDs, kinds and scheduling fields, never targets, CA bytes or remote responses. Existing saved HTTPS checks without `tls_alert_days` remain off after upgrade. An older client omitting `tls_alert_days` or `ca_cert_der_b64` on an unchanged target preserves its saved value; explicit `null` turns off the alert or removes the custom CA. A target change with either field omitted resets that value. A rule change retires the old certificate incident and discards unsent notifications without implying renewal; the next Agent result evaluates the new rule.

Manual run schedules an enabled check for the next Agent poll. It does not probe from Hub, enable a disabled check or create concurrent duplicate work. Disabled/inflight checks and stale revisions return `409`; another successful manual request within ten seconds returns `429`. Automatic scheduling starts at completion plus interval, without accumulating missed runs.

`CheckLease` contains exactly `id` (canonical UUID), `check_id`, `config_revision`, `expires_at` and `check` (the executable `CheckDefinition`, without Hub-only `tls_alert_days` or a null CA). A non-null custom CA travels only to that server's authenticated Agent. The complete serialized lease response is bounded to 4096 bytes for the Agent helper protocol. Leases last 90 seconds by Hub time; at most one is active per check and two per server. A valid protocol-1 claim updates `worker_seen_at`, including when no work is available. Agent credentials are checked inside the same SQLite transaction as claim/result acceptance. Token rotation invalidates active leases; the new token cannot complete an old token's work.

Agent result input contains exactly `lease_id`, `config_revision` and these six fields:

```json
{"observed_at":1790000000,"status":"up","latency_ms":42,"http_status":200,"tls_expires_at":1797000000,"error_code":null}
```

`observed_at` and nullable `tls_expires_at` are integer Unix seconds in 1–253402300799; observation time must be within five minutes of Hub time. `latency_ms` is an integer 0–10000. `status` is `up` or `down`. Nullable `http_status` is an integer 100–599. Nullable `error_code` is one of `dns_error`, `dns_mismatch`, `connect_error`, `tls_error`, `timeout`, `http_error`, `invalid_response`, `internal_error`. Up requires no error; down requires one. Successful HTTP requires 2xx; `http_error` requires a non-2xx status. TCP and DNS always have null HTTP/TLS fields. `dns_mismatch` means a valid answer did not contain the configured expected IP; DNS resolution failures use `dns_error`. Plain HTTP has no TLS expiry. Successful HTTPS requires a verified certificate expiry; untrusted, expired or wrong-host certificates produce `tls_error` without an expiry. Verified expiry may remain visible when HTTP subsequently fails or times out.

Agents GET without redirects, authentication headers, cookies or request bodies. They read at most 32 KiB of status/headers, never response bodies. The parent bounds DNS and total probe lifetime. No resolved IP, reason phrase, response header/body or exception text enters the result schema. HTTPS uses the system trust store plus the optional configured CA, with mandatory chain and hostname verification; there is no insecure override. TCP success proves only that a connection was accepted.

Result acceptance checks server, check, lease, token generation, config revision and expiry transactionally. Deleted, changed, expired or foreign leases return `409`; invalid credentials return `401`. An identical completed-result replay succeeds without adding history or changing receipt time/schedule while its original lease remains valid and its history row exists; a different replay returns `409`. At most 60 rows per check are retained, pruning results and their idempotency metadata on every result write, independently of UI reads.

Summary returns `{ "server_id", "revision", "worker_seen_at", "checks": [...] }`. Items contain only `id`, `name`, `kind`, `enabled`, `interval_seconds`, `timeout_seconds`, nullable effective `tls_alert_days`, nullable `latest` and `state`. `CheckResult` in latest/history contains the six result fields above plus integer `received_at`; targets, lease IDs and token hashes are omitted. All Hub roles can read summary/history; target configuration and manual runs require admin. History accepts one optional `limit` parameter (1–60, default 60), newest first.

States: `disabled`, `waiting` (no result), `up`, `down`, `stale`. A report becomes stale when its receipt is older than `max(90, 2 × interval_seconds)`, or worker polling is absent/older than `max(90, offline_seconds)`. Worker freshness is independent of metrics. Missing/stale results do not invent a confirmed target failure. Web separately warns about verified certificates expiring within 14 days.

An accepted `down` result starts a candidate for incident kind `check:<check_id>`. The global `trigger_minutes` delay applies; another accepted `down` result at or after that delay confirms the incident. An interval without a result longer than `max(90, 2 × interval_seconds)` restarts the candidate, because continuous failure is unproven. An accepted `up` result clears a candidate or resolves a firing incident. Replayed results do not create another transition. Disabling/deleting a check or changing its target or CA ends its active incident, clears the candidate and discards undelivered messages without claiming a recovery. Maintenance suppresses Telegram notifications and creates one reminder if the incident still fires when the window ends. Telegram uses a short check ID in messages rather than the administrator-editable name or target; the authenticated Web panel shows the saved name. With `tls_alert_days` enabled, a result carrying a **verified** HTTPS certificate expiry at or within the configured number of days starts a separate `tls:<check_id>` candidate. Hub compares UTC Unix seconds, applies the global hold and sample-gap rules, and creates a firing incident after confirmation if a hold is configured. A later verified certificate with more time remaining resolves it. A result without verified expiry clears an unconfirmed candidate but leaves an already-firing expiry incident open: a failed TLS handshake cannot prove renewal. A check can have outage and expiry incidents at the same time. Replayed results add no transition. Maintenance reminders and recovery use the same durable, role-checked outbox; Telegram includes a short check ID and remaining days, never the URL or editable name. The Web certificate warning at 14 days is independent of this opt-in backend alert; disabling a saved alert sends explicit `null`.

### Managed container logs

This backend has no browser control yet. The dedicated route accepts only a full lowercase 64-hex container ID from the Agent's latest complete Docker or Podman inventory. The Agent rejects the reserved marker on general command paths. The root broker requires the Agent's exact systemd MainPID in addition to its Unix UID, so an ordinary shell command under the same UID cannot call that broker socket. Rootless/nondefault Engine sockets and containers outside this SovaGrid Compose project are not supported by this action.

### Exact Docker container actions (backend contract)

The Hub source accepts the four fixed actions above only for an exact ID in the newest complete Docker inventory received from an online Agent within 120 seconds. Obvious SovaGrid, Amnezia, SSH, tunnel, VPN and container-engine workloads are refused at Hub; the Agent's root broker independently checks its root-owned exact ID/name/image policy and live inspect before every operation. ### Opt-in Docker container alarms

`GET /api/v1/servers/{id}/containers/alerts` requires a viewer session with access to that server. It returns `{ "revision":0, "hold_seconds":120, "rules":[], "source_status":"unavailable", "observed_at":null, "observations":[] }` until configured. `PUT` on the same path requires a server-scoped administrator and accepts **only** `{ "revision", "hold_seconds", "rules" }`. A rule is `{ "name":"api-service", "stopped":true, "unhealthy":true, "missing":false }`; at least one condition must be true. Names are exact, case-sensitive Docker names matching `[A-Za-z0-9][A-Za-z0-9_.-]{0,95}`. Up to 12 unique names are allowed; `hold_seconds` is 0–86400. New names must appear in the latest complete Docker list, while an existing rule can be edited or removed if its server is offline. `revision` is a compare-and-swap value; a stale revision or unavailable new selection returns 409, an invalid payload returns 400. PUT returns the same object as GET with the next revision. Query parameters and duplicate JSON fields are rejected.

`source_status` is `ok`, `stale`, `partial` or `unavailable`. `observed_at` is the Docker snapshot's UTC epoch, distinct from the later metric collection time. Freshness compares Hub receipt with Hub current time and compares Docker snapshot time with the Agent metric time; it never directly compares clocks on different machines. `observations` follows rule order and contains `{ "name", "status" }`, where status is `running`, `stopped`, `unhealthy`, `missing` or `unknown`. A running container with no health check or with health `starting` is `running`; only Engine health `unhealthy` is `unhealthy`. Paused, restarting, created, removing, exited and dead states are `stopped`. An absent name is `missing` **only** in a fresh complete Docker list. A clipped list, missing collector, unsupported state or stale report yields `unknown` and cannot resolve an incident.

Rules are off by default. A breach requires a new root collector snapshot and, when a hold is set, another fresh snapshot at or after the hold. Replayed snapshots and older delayed metrics do not advance the hold. A firing incident has kind `container:` plus SHA-256 of the configured name; its `subject` contains the name for authenticated panel viewers. Telegram uses only the first eight hash digits, never the name, image or container ID. A healthy complete observation resolves the incident. Disabling or changing a rule retires its old incident and undelivered notifications without claiming a measured recovery. Maintenance windows and the durable Telegram outbox apply as for other incidents. Configured names and incident subjects are stored in SQLite; complete container inventories remain transient and absent from metric history.

### Opt-in alerts for individual filesystems

`GET /api/v1/servers/{id}/filesystems/alerts` requires viewer access to that server and returns `server_id`, `revision`, `hold_seconds`, `rules`, `source_status`, `observed_at`, `filesystems` and `observations`. New servers have revision 0, a 120-second hold and no rules. `PUT` on the same path requires server-scoped admin access and accepts exactly `{ "revision", "hold_seconds", "rules" }`. The hold is 0–86400 seconds. Up to 32 rules are allowed, one per `(mountpoint, metric)` pair. A rule is `{ "mountpoint":"/var/data", "metric":"space", "threshold_percent":80 }`; metric is `space` or `inodes`, and the threshold is an integer 1–100. The mountpoint is an exact, canonical absolute POSIX path of at most 128 UTF-8 bytes. A new pair must be present with a usable count in the latest fresh, non-truncated inventory. Existing rules can be edited or removed when telemetry is unavailable. A stale CAS revision or unavailable new selection returns 409. Invalid fields, duplicate JSON keys and query parameters are rejected. Every successful PUT advances revision by one and returns the current GET shape.

`source_status` is `ok`, `partial`, `stale` or `unavailable`. Only `ok` includes selectable `filesystems`, each with `mountpoint`, `fstype`, `space_used_percent` and `inodes_used_percent`; a percentage is null when its total count is zero. `partial` includes an Agent truncation flag, a 16-row legacy list or contradictory counters. `observations` contains each rule's `mountpoint`, `metric`, `status` (`normal`, `alert` or `unknown`) and nullable `used_percent`. Hub recomputes percentages from total and available counters. A valid present row can confirm a configured rule even when another mountpoint was clipped. Missing, stale, unsupported or contradictory data never resolves an incident and clears an unconfirmed hold. A missing mountpoint is always unknown because older Agents may silently trim their list. Freshness uses Hub receipt time so different host clock offsets do not suppress valid reports; each Agent collection timestamp can advance a hold only once.

Each breach is opt-in and creates an incident kind `filesystem:space:` or `filesystem:inodes:` followed by SHA-256 of the metric and mountpoint. Its authenticated panel subject is the mountpoint; Telegram receives only a short hash, never the path. Rule changes retire the previous incident and undelivered notifications without claiming measured recovery. Maintenance windows and the durable Telegram outbox apply. This rule is independent of the global root inode and whole-server disk thresholds.

### Read-only systemd journal

The browser requests an exact unit and 1–100 lines through `POST /api/v1/servers/{id}/journal` after a confirmation. Hub requires an admin session, `remote_commands_enabled`, an online Agent report advertising that exact unit, and an idempotency key. A second **new** request from the same session/server within 20 seconds returns `429`; replay of the same idempotency key still returns the original job. Only the broker gets `systemd-journal` group access. It executes fixed `journalctl` arguments without a shell, reading only the last 24 hours with a five-second and 8 KiB bound. A Hub admin with general command permission can still run any command that the `sovagrid` OS user is otherwise allowed to run, including speaking the broker socket for allowed units; general job output persists in the usual job history. The general `GET /api/v1/jobs` list never contains this action's journal text.

### On-demand process inventory

`POST /api/v1/servers/{id}/processes/snapshot` uses the same Hub and Agent command opt-ins as other jobs and requires an admin grant for that server. `after_pid` is a cursor from 0 through 2³¹−1, `limit` is 1–32, and `filter` is an optional case-insensitive substring of the short process name, at most 16 characters. Start with `after_pid:0`; use `next_after_pid` while `has_more` is true. Each page enumerates PID names with a five-second budget and reads at most 2048 process directories. A live process table can change between pages. Successful job output is JSON with exactly `observed_at` (UTC epoch seconds), `after_pid`, `filter`, `next_after_pid`, `has_more`, and `processes` (PID, short name, RSS bytes). Agent reads only `comm` and `statm`, never command arguments, environment or executable paths. Unreadable or exited processes are skipped. Hub verifies the filter against its audited digest, every returned name and the 8 KiB result cap.

Only the requesting admin session may read a page via `GET /api/v1/jobs/{job_id}`. Hub keeps it in the same bounded five-minute memory cache as structured journal output; SQLite stores only job state, empty output and audit metadata without observed process names. Logout, password change or Hub restart clears it sooner. Malformed Agent output becomes a fixed failure. The general jobs list never contains page content. General shell commands such as `ps` remain administrator actions and use normal persistent job history.

The filesystem, interface, disk, and service arrays accept at most 16 entries each. Mountpoints are limited to 128 printable characters, interface and device names to 64, filesystem types to 32. `top_processes` accepts at most 10 unique positive PIDs, names of 1–16 ASCII letters, numbers or punctuation from a narrow allowlist, and positive 64-bit RSS byte counts. No argv, environment, user names, or executable paths are accepted. The serialized `details` object is limited to 12 KiB; the full request body is limited to 16 KiB. Unknown categories, extra nested keys, negative counters, nonfinite numbers, duplicate names/PIDs, and values outside the percentage range are rejected. Hub stores all other `details` fields in SQLite, but holds `top_processes` and `containers` only in process memory for the newest report. Container inventory is available to authenticated Hub roles in `ServerSummary.latest`, including when the source becomes stale; its data never enters metric history, SQLite, jobs, or audit. Restarting Hub clears transient lists until the next Agent report. Hub automatically adds the `details` column to databases from the previous MVP when `serve` starts.

`details.pressure` is an optional fixed-cardinality Linux PSI object. It may contain any available subset of `cpu`, `memory`, and `io`. `cpu` has exactly `some`; `memory` and `io` each have exactly `some` and `full`. Every mode has `{ "avg10", "avg60", "avg300", "total_us" }`: three percentages in `[0,100]` and a nonnegative signed-64-bit microsecond counter. `details.cpu_times` is optional and has exactly `{ "iowait_percent", "steal_percent" }`, each in `[0,100]`. These fields contain no free-form labels. Both are stored in SQLite and returned in `ServerSummary.latest` and oldest-first metric history. Older history rows omit them. A new Agent initially sends its existing metric shape, enables only the exact categories advertised by a successful Hub response, and retries once without these categories after a `422` on a previously negotiated report.

`details.clock` is an optional read-only Agent diagnostic with exactly `system_utc_epoch` (positive Unix UTC seconds), `timezone` (IANA-style name or null), `ntp_synchronized` (boolean or null), `rtc_local_time` (boolean or null), `rtc_utc_epoch` (positive Unix UTC seconds or null), and `rtc_offset_seconds` (integer seconds or null). The RTC fields are either both null, or `rtc_local_time` is false and `rtc_offset_seconds` equals `rtc_utc_epoch - system_utc_epoch`. Null means the Agent could not verify the value. This offset compares the hardware clock with the system clock; it is not an NTP measurement or a timezone correction. Clients should treat the epoch values as UTC and format display times in the viewer's chosen timezone. The diagnostic never changes the host clock.

`Incident` has `id`, `server_id`, `server_name` (in list response), `kind` (`high_cpu`, `high_memory`, `high_disk`, `high_root_inodes`, `failed_services`, `offline`, `check:<check_id>` or `tls:<check_id>`), `state` (`firing` or `resolved`), `opened_at`, `updated_at`, nullable `resolved_at`, nullable `acknowledged_at`, `current_value`, `threshold`, nullable `alerted_at`, and nullable `subject` (the check name for check/TLS incidents). For `tls:` incidents, `current_value` and `threshold` are days remaining and configured alert days, not percentages; for `high_root_inodes` they are percentages. The new `subject` column is added to existing SQLite databases without discarding incident history. When a hold is configured, `opened_at` records the first observed breach, even though the incident appears only after the hold. `alerted_at` records when a firing transition became eligible for Telegram; it does not prove any recipient existed or Telegram delivered it. Recovery notifications are claimed only for incidents with `alerted_at` and outside maintenance. The Web history always shows recovery from `resolved_at`, regardless of Telegram delivery.

The VPN inventory is a read-only snapshot produced by a root-owned local timer. The Amnezia/Docker `source_status` and `managed.source_status` are independent and may each be `ok`, `stale` (over 90 seconds old), `error`, or `unavailable`. Only exact known Amnezia service names, state, health, and published TCP/UDP port numbers pass validation. Managed instances contain only the name, interface, port, subnet, client count, and state. The Hub never receives Docker socket access or VPN keys. Container state alone does not prove client connectivity.

No received snapshot means `received_at:null`, `freshness:"unavailable"`, and an empty `vpn` projection with `source_status:"unavailable"` for each source. More than 90 seconds after Hub receipt, `freshness` becomes `stale` and only source statuses that were `ok` become `stale`; source errors and unavailable sources remain distinct. Clients should use `received_at` and `freshness` for age because Agent and Hub clocks may differ; `vpn.collected_at` is the source host's timestamp. Agent-token POSTs are separate from metrics, reject duplicate JSON fields, and only the strict sanitized projection enters SQLite, replacing the previous snapshot for that server. A missing route on an older Hub returns `404` and the Agent continues. A viewer without that server's grant receives `403`; a missing or expired user session receives `401`.

### Optional systemd service control

`POST /api/v1/servers/{id}/services/actions` creates a job for exactly one allowlisted `.service` unit. The Agent uses a separate, default-off root broker with an independent per-unit action policy. Hub and Agent accept no arbitrary `systemctl` options, unit paths or shell syntax in this route. The unit must start with an ASCII letter or digit, contain up to 88 ASCII letters, digits, `_`, `.`, `@`, or `-` before `.service`, and cannot be an uninstantiated `@.service` template. A root administrator arms the Agent policy separately; Hub cannot bypass it. Mutations of SovaGrid, SSH, tunnel, network, container-engine, firewall and VPN access units return `403` before queuing; their `status` action remains available. Agent's root broker repeats the protected-unit check and rejects a mutation if systemd's actual unit ID or any alias is protected or cannot be verified before execution. A host administrator still must review dependencies and impact of every other unit in the local allowlist.

The generic Web `/jobs` endpoint and Telegram command queue reject service, managed VPN, and Amnezia control markers before a job is queued, including wrapped commands and whitespace between the marker and arguments. Queued jobs carry a control kind set only by their structured endpoint; Agent polling cancels legacy generic jobs containing these markers after database migration. A same-UID shell could otherwise open the Unix socket directly, so the root brokers also require the peer PID to equal the current systemd MainPID of the exact Agent unit; the Agent starts nondumpable to keep its memory and file descriptors inaccessible to command children. This OS boundary, plus the root-owned policy, is authoritative. Generic string filtering prevents accidental use of the structured protocol. Keep service mutation policy disabled until both Agent and broker have this boundary installed; existing live policies remain status-only.

Queue `status` first, then read its job or `GET /api/v1/servers/{id}/services/control?unit=NAME.service`. Hub permits `start`, `stop`, or `restart` only after a successful `status` for the **same unit on the same server** in the past 90 seconds. Any later mutation job, including queued, failed or timed-out jobs, invalidates that probe; a new successful status must finish strictly after every earlier mutation finishes. A missing, stale or invalidated probe returns `503` for mutation and `source_status:"unavailable"` for control; invalid input returns `400`; missing Hub command permission returns `403`. The Agent broker checks the local policy again when the job executes. The successful status response has only `action`, `unit`, `result`, `load_state`, `active_state`, and `sub_state`; it contains no raw journal or systemctl output. For a mutation, `result:"uncertain"` and job state `timed_out` mean the action may have taken effect: recheck status before retrying. All service jobs use the normal idempotency key and audit path. The Agent broker request is bounded to 55 seconds and the Hub advertises a 60-second job timeout.

The Web panel asks the admin to confirm a mutation. An admin may also use this structured API directly after the successful status probe; Hub applies the same admin session, server access, idempotency, and freshness checks in either case.

### Job schema

`JobSummary` has `id`, `server_id`, `server_name`, `source` (`web` or `telegram`), `actor_user_id`, `chat_id`, `state`, `created_at`, `delivered_at`, `completed_at`, `exit_code`, and `output`. For web jobs, the Telegram actor IDs are `0`; they are not user identities. The command text is deliberately absent from both list and detail responses. Job state is `queued`, `delivered`, `succeeded`, `failed`, `timed_out`, `output_limited`, or `cancelled`. The result endpoint accepts only terminal states. Outputs may contain sensitive data and are visible only to Hub admin and the Telegram admin who requested that job. The list substitutes an empty `output` for AWG3 settings-intent confirmations and any result carrying a `confirmation_id`; the admin-scoped single-job endpoint retains the complete result for the temporary confirmation flow.

Web jobs require a valid admin bearer session and the server's `remote_commands_enabled=true`. The generic `/jobs` request body accepts only `command`: 1–2048 UTF-8 bytes after trimming, with no NUL. Generic jobs use a 15-second timeout; exact managed WireGuard broker commands use 105 seconds, and exact optional Amnezia broker commands use 135 seconds. All jobs have an 8192-byte output cap. Clients cannot raise these limits. The Ubuntu agent must separately set `allow_remote_commands=true` in its root-controlled local config before it will poll for jobs. Admin bearer tokens are sent in the `Authorization` header, never cookies, so a cross-site form cannot authorize a command. Hub stores only the session token hash on a queued web job. Logout, admin password change, or session expiry cancels web jobs that have not yet been delivered. A delivered job cannot be recalled, even if the admin session ends. Use `GET /api/v1/jobs/{job_id}` to poll for its result. The optional `Idempotency-Key` header for generic `/jobs` must be a canonical UUID generated once per command confirmation and reused for retries within that admin session. The same key and command returns the original job (including its current state) with HTTP `200`; reuse for another server or command returns `409`. This prevents accidental duplicate execution after a client timeout.

## Interactive terminal

An interactive terminal uses the same Hub admin bearer session and server `remote_commands_enabled` opt-in as web jobs. The Agent must additionally have both `allow_remote_commands=true` and `allow_interactive_terminal=true` in its root-controlled local config. It opens a PTY through a local Unix-socket broker as the separate `sovagrid-shell` OS user; the browser never connects to the Agent directly. All Agent requests are outbound HTTPS with the server's Agent bearer token. The Hub holds terminal bytes only in bounded process memory and never writes them to SQLite, jobs, audit details, or Telegram.

| Method | Endpoint | Caller | Body / response |
| --- | --- | --- | --- |
| POST | `/api/v1/servers/{server_id}/terminal/sessions` | Admin | Exact `{"cols":80,"rows":24}`, one canonical UUID `Idempotency-Key`; `201` new / `200` replay with `{"session":{"id","server_id","state":"pending","created_at"}}` |
| GET | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/events?after=N` | Owning admin session | Up to 15-second long poll; `{"events":[{"seq":1,"type":"output","data":"<base64url>"}],"next_after":1,"state":"active","exit_code":null,"reason":null}` |
| POST | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/input` | Owning admin session | Exact `{"seq":1,"data":"<base64url>"}`; `202` accepted, `200` identical replay |
| POST | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/resize` | Owning admin session | Exact `{"seq":2,"cols":100,"rows":30}`; shares the input sequence |
| DELETE | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}` | Owning admin session | `200 {"closed":true}` |
| GET | `/api/v1/servers/{server_id}/terminal/next` | Agent | Up to 15-second long poll; `{"session":null}` or `{"session":{"id","cols","rows"}}` |
| POST | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/ready` | Agent | Exact `{}`; marks the PTY active |
| GET | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/controls?after=N` | Agent | Up to 15-second long poll; ordered input and resize events, `next_after`, `state`, and `reason` |
| POST | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/output` | Agent | Exact `{"seq":1,"data":"<base64url>"}`; `202` accepted, `200` identical replay |
| POST | `/api/v1/servers/{server_id}/terminal/sessions/{session_id}/exit` | Agent | Exact `{"exit_code":null}` or bounded integer; closes the session |

All binary frames are canonical, unpadded base64url with 1–4096 decoded bytes. Browser input and resize use one monotonically increasing sequence; Agent output uses a separate sequence. Each `after` acknowledges delivered frames, so retry a lost response with the same cursor. A gap or conflicting replay returns `409`; an expired output cursor closes the session. Sizes are 20–300 columns and 10–120 rows. The Hub permits one active session per server, four globally, 32 concurrent long-poll waiters globally, and at most one waiter of each type per session/server. Per-session unacknowledged output is capped at 512 KiB, input at 64 KiB. Browser inactivity for 90 seconds, an absolute lifetime of 30 minutes, logout, session expiry, password change, Agent token rotation, or command disablement closes the terminal. Closed output is retained for at most 30 seconds. A Hub restart loses active sessions; the Agent closes its PTY after the relay disappears. The browser should use a request timeout above 15 seconds and display `closed` with `reason` rather than silently reconnecting to a new shell.

## File browser, text editor, and binary transfer

File operations require the Hub admin session, `remote_commands_enabled=true` for the exact server, and the Agent's separate local `allow_remote_commands=true`, `allow_file_manager=true`, and explicit `file_roots`. The Agent initiates every connection over verified HTTPS; no inbound file service or shell command is used. This feature is off by default. A root alias reveals only its name to the browser, not its absolute path. File operations run as the unprivileged Agent OS user. They are confined to configured roots using directory descriptors and `O_NOFOLLOW` for every path component; symlinks, hard-linked files, devices, sockets, and FIFOs are rejected. The text editor additionally rejects non-UTF-8/NUL content. Writes require a private Agent-owned parent directory; overwriting also requires an Agent-owned regular file without hard links.

| Method | Endpoint | Caller | Body / response |
| --- | --- | --- | --- |
| POST | `/api/v1/servers/{server_id}/files/operations` | Admin | One canonical UUID `Idempotency-Key`; exact body `{"action":"roots"}`, `{"action":"list","root":"workspace","path":"subdir"}`, `{"action":"read","root":"workspace","path":"subdir/file.txt"}`, or `{"action":"write","root":"workspace","path":"subdir/file.txt","etag":"<64 lowercase hex>","content":"<base64url UTF-8>"}`. Returns `201` new / `200` replay with `{"operation":{"id","state"}}` |
| GET | `/api/v1/servers/{server_id}/files/operations/{operation_id}` | Owning admin session | `{"operation":{"id","state","result"}}`; state is `queued`, `running`, `succeeded`, or `failed`. Successful result is `{"roots":[names]}`, `{"entries":[{"name","kind","size"}],"truncated":bool}`, `{"content":"<base64url>","etag","size"}`, or `{"etag","size"}`. Failed result is `{"code":"..."}` |
| GET | `/api/v1/servers/{server_id}/files/next` | Agent | Eight-second long poll; `{"operation":null}` or `{"operation":{"id","request"}}` |
| POST | `/api/v1/servers/{server_id}/files/operations/{operation_id}/result` | Agent | Exact `{"state":"succeeded","value":{...}}` or `{"state":"failed","code":"..."}` |
| DELETE | `/api/v1/servers/{server_id}/files/operations/{operation_id}` | Owning admin session | Releases a finished transfer result from Hub memory early; `{"closed":true}` |

Text contents are canonical unpadded base64url with at most 8192 decoded UTF-8 bytes. Binary transfer actions use the same operation endpoint with these exact bodies (all hashes and ETags are 64 lowercase hex characters):

| Action | Request | Successful result |
| --- | --- | --- |
| `binary_info` | `{action,root,path}` | `{size,etag,sha256}` for a regular file up to 32 MiB for download |
| `binary_chunk` | `{action,root,path,etag,offset}` | `{content,offset,size,etag}`; offset is a 64 KiB multiple, content at most 64 KiB canonical base64url |
| `upload_begin` | `{action,root,path,size,sha256,etag}` | `{upload_id,size}`; `etag:null` means create only, otherwise replace that exact version |
| `upload_chunk` | `{action,root,path,upload_id,offset,content}` | `{received,size}`; chunks append at the exact current offset |
| `upload_commit` | `{action,root,path,upload_id}` | `{size,sha256,etag}` after atomic replacement |
| `upload_cancel` | `{action,root,path,upload_id}` | `{cancelled:true}`; also expires after ten idle minutes or Agent restart |

The file routes alone accept a 90 KiB JSON body for a 64 KiB binary chunk; all other routes retain the 16 KiB limit. Agent holds at most four upload sessions of 4 MiB each in memory, checks whole-file SHA-256 before commit, and rechecks the target ETag or new-file absence. Binary downloads are capped at 32 MiB. Download chunks check the file's descriptor metadata on every read; the browser verifies the whole-file digest before saving. Paths are relative to one root, at most 512 UTF-8 bytes, with no empty, `.` or `..` components. At most 200 entries and 12 KiB of serialized entry data are returned per listing. Eight roots may be configured, 64 operations may be active globally, and 32 per admin session. Only one Agent file poll per server and 16 such polls globally may wait at once; excess polls return `429`. Operations expire after 120 seconds. Hub stores requests and results only in bounded process memory; restart drops them. The SQLite audit records action, operation ID, server ID, outcome, and a path hash, never a path or file bytes. Logout, Agent token rotation, and command disablement clear pending file operations. A stale ETag yields `conflict`; the browser keeps unsaved edits. The Agent checks the file again immediately before atomic replacement, but unrelated processes writing the same file without coordination can still race that final replacement. Use a private, Agent-owned root for editing. Supported failure codes include `disabled`, `not_found`, `unsupported`, `too_large`, `conflict`, `denied`, `busy`, and `unavailable`.

Removing or demoting a Telegram admin binding deletes its pending confirmations and cancels its queued jobs. Confirmation and agent lease both recheck the current admin binding. A job already delivered to an agent cannot be withdrawn; result reports for delivered jobs remain valid.

`AuditEvent` has `id`, `at`, `actor`, `action`, `server_id`, `subject_id`, and JSON-encoded `details`. The audit log never stores command text, only its SHA-256 digest. It records web command queueing, delivery, completion, and cancellation. Plaintext remains in the protected jobs table only while queued; Hub clears it atomically when the agent leases the job or the job is cancelled. The command digest remains for idempotent retries.

Error responses have `{ "error": "…" }`; relevant statuses include 400, 401, 403, 404, 408, 409, 413, 415, 422, and 429.
