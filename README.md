# SovaGrid Hub

Self-hosted Ubuntu control plane for SovaGrid. This first version uses only Python 3 standard-library modules. It stores server metrics and incidents in SQLite, serves a loopback JSON API, and can send Telegram alerts. An enrolled Linux agent may receive a command from the Hub admin panel or a confirmed Telegram admin only when both sides enable remote commands.

## Install on Ubuntu

Python 3.10 or newer is required. Run Hub and the agent as separate, unprivileged service accounts.

```sh
sudo useradd --system --home-dir /var/lib/sovagrid-hub --shell /usr/sbin/nologin sovagrid-hub
sudo install -d -o sovagrid-hub -g sovagrid-hub -m 0700 /var/lib/sovagrid-hub
sudo install -d -m 0755 /opt/sovagrid-hub
sudo cp -R sovagrid_hub /opt/sovagrid-hub/
sudo chown -R root:root /opt/sovagrid-hub
sudo -u sovagrid-hub sh -c 'cd /opt/sovagrid-hub && python3 -m sovagrid_hub --db /var/lib/sovagrid-hub/hub.sqlite init'
sudo cp deploy/sovagrid-hub.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now sovagrid-hub
```

`init` asks for an admin password with at least 12 characters and refuses to replace an existing database. It creates the database with mode `0600`. The password uses scrypt with a random salt. Admin session and agent tokens are stored only as hashes; the API returns the agent token only when a server is created or its token is rotated. Change the admin password in **Web → Настройки → Сменить пароль**: enter the current password, a new password, and its confirmation. Hub revokes that account's sessions, closes its browser terminals and pending file operations, and cancels its queued web jobs; sign in again with the new password. The CLI `python3 -m sovagrid_hub --db /var/lib/sovagrid-hub/hub.sqlite passwd` remains a recovery option.

The deployment's `/etc/sovagrid/admin-password` file is an initial-password record created by `run.sh`, not a live password source. A change in Web updates the Hub database and **does not update that file**; any old value there no longer works for login. Keep the file protected or remove the stale copy using your usual server administration process.

Set monitoring alert levels in **Web → Настройки → Когда сообщать о проблеме**. CPU, memory and root-disk percentages, the time without metric updates, and an optional sustained-problem delay are saved in SQLite and applied without restarting Hub. The delay defaults to zero (immediate alerts) and can be set from 1 minute to 24 hours. A short spike that clears before confirmation creates no incident. Pending conditions survive Hub restarts; CPU, memory, disk and service problems require another Agent sample to confirm, while offline detection uses the ten-second sweep. The panel warns if another administrator changes the settings before you save. The command-line threshold options remain defaults for installations that have not saved settings through the panel.

Hub also supports immediate, per-server maintenance windows in the Web panel and admin API. `POST /api/v1/servers/{id}/maintenance` accepts an end time and a short reason; `GET` on the same path lists active and recent windows, and `DELETE /api/v1/servers/{id}/maintenance/{window_id}` ends one early. A window can last from one minute to seven days. Metrics and incidents remain visible throughout it, but Telegram alert delivery for that server is quiet. If an incident is still active when the window ends, the sweep sends one alert; a problem that cleared during maintenance does not produce a delayed false alarm. Window changes and their reasons appear in the Hub audit log. See [API.md](API.md) for exact fields and response codes.

The HTTP server binds to **`127.0.0.1` by default**. Put a TLS reverse proxy in front of it. [deploy/Caddyfile.example](deploy/Caddyfile.example) serves the browser client and API under one HTTPS origin; replace its hostname and web root before using it. Never expose port 8765 or the SQLite database directly to the internet. `serve --bind 0.0.0.0` is available for a Hub container reachable only inside a closed Docker bridge network; publish only the frontend on the host loopback interface for a local test, and never publish the Hub port. In that setup, point Caddy's upstream at the Hub container and use a fixed Caddy container IP with `serve --trusted-proxy <Caddy-IPv4>`.

Caddy must overwrite `X-SovaGrid-Client-IP` with `{remote_host}` as in the example. Hub accepts that header only from loopback or an explicit `--trusted-proxy` address; all other peers are identified by their socket address. Login failures are limited per source IP (five failures, then 30 seconds). A trusted proxy address must belong only to your proxy, because another process at that address could spoof source IPs. HTTP request reads have a 10-second timeout; incomplete bodies receive `408`.

Configure optional HTTP/HTTPS, TCP and DNS A/AAAA checks in **Web → Обзор → Сетевые проверки**. Add targets explicitly for one enrolled server; there are no automatic probes or default targets. The Agent checks them through two isolated workers, independently of metric collection and remote commands. The panel shows current status, freshness, up to 60 recent results and verified HTTPS certificate expiry. Targets and scheduling are admin-only; viewers/operators receive sanitized statuses without addresses. HTTPS verifies the system trust chain and hostname; HTTP redirects and response bodies are not followed/read. A sustained failed check raises an incident using the global alert delay, then resolves on a successful result. Telegram sends firing and recovery messages through the same durable, maintenance-aware outbox as server alerts; messages use a short check ID and never include the target or editable check name. An administrator may opt into a 1–90 day certificate expiry incident for each HTTPS check through `tls_alert_days`; existing checks keep this rule disabled. Verified expiry, renewal and maintenance reminders use the same durable outbox. Existing metrics, sessions and configuration survive the additive SQLite migration. See [API.md](API.md) for limits, roles, result semantics and lease guarantees.

Docker container alarms are separately opt-in per server. An administrator selects up to 12 exact container names from a fresh complete Docker inventory and chooses whether stopped, unhealthy, or missing should alert. Each rule uses a compare-and-swap revision and a 0–24 hour confirmation hold. A stale, partial or unavailable inventory cannot claim recovery; repeated collector snapshots do not advance a pending alert. The same maintenance-aware Telegram outbox delivers confirmed incidents without including container names in the message. See [API.md](API.md) for the `GET`/`PUT /api/v1/servers/{id}/containers/alerts` contract. No Docker control permission is needed for read-only monitoring.

## Register a server

Login using `POST /api/v1/session`, then call `POST /api/v1/servers` with `{"name":"my-ubuntu"}` and the session bearer token. Save the returned `id` and `agent_token` for the agent. See [API.md](API.md) for the complete contract. The Hub can run on the same Ubuntu machine that it monitors, but **it cannot send an offline alert if that entire machine or its network fails**. For that case, run an external watcher or another Hub elsewhere.

## Telegram

Create a bot with BotFather. Log in as the Hub admin, open **Telegram** in the Web panel, and paste the token there. Hub verifies it with Telegram's `getMe` before saving it to `telegram-bot-token` beside the SQLite database (`/var/lib/sovagrid-hub/telegram-bot-token` for the systemd service, `/data/telegram-bot-token` in the Blueprint container). The Hub owns this file with mode `0600`; the token is never returned by the API or written to the audit log. Saving or replacing it starts the bot without a Hub restart. Removing it stops polling. A token whose verification fails is not saved, and an existing token remains active.

1. Open the bot from the panel's link, if available, or find the bot you created in BotFather. Send `/start` in a private chat. The bot creates a pending request; it has no command access yet.
2. In the panel, review the displayed Telegram name and approve the request with a `viewer`, `operator`, or `admin` role, or reject it. The bot notifies the requester. No numeric ID or server console command is needed for this flow.
3. `/help` lists commands allowed for the approved role. `viewer` can use `/status`, `/checks`, `/vpn`, and `/alerts`; `operator` can also `/ack`; `admin` can additionally use `/exec`, `/confirm`, and `/result`.

Pending requests expire after seven days; at most 100 may wait at once. A rejected user cannot submit another request for 24 hours. An existing approved user can be assigned a different role in the panel. For advanced manual recovery, `/whoami` returns the private IDs, and the panel's manual binding form or `bot-user add --user-id ... --chat-id ... --role ...` can add them. In a private chat both IDs must match.

For a legacy file managed by the host, save the token in `/etc/sovagrid-hub/bot.token`, owned by `root:sovagrid-hub`, mode `0640`, and install [deploy/telegram-override.conf](deploy/telegram-override.conf) as `/etc/systemd/system/sovagrid-hub.service.d/telegram.conf`. Reload systemd and restart the Hub. The panel displays this as externally managed and cannot replace or remove that file, though it can manage bindings. Keep the token out of command-line arguments and the repository.

The bot accepts commands only from bound private `(user_id, chat_id)` pairs. Hub uses Telegram long polling and sends notifications to bound chats. `/exec <server_id> <command>` creates a one-time 60-second confirmation code; only the same admin user and chat can use `/confirm <code>`. A command is sent to an agent only if Hub's `remote_commands_enabled` is true for that server **and** the agent's local `allow_remote_commands` is true. Enable the Hub side with `POST /api/v1/servers/<id>/commands` and `{"enabled":true}` while logged in as admin. The separate `sovagrid-agent` README describes the agent side.

Hub records each Telegram update ID before handling it. A crash at that instant can drop one update, which the user may resend; restarting Hub or replacing the bot token cannot replay an already claimed command update. Update cursors are kept separately for each bot token digest.

`/vpn` reads the same sanitized host inventory as the panel. It reports Docker container state and Docker health for recognized Amnezia services and, when available, the state and configured client count of managed WireGuard instances. It never sends VPN keys, client addresses, profiles, or server subnets. Missing, stale, and failed inventory sources are shown explicitly. A running container or active service does not prove that a VPN connection works or that a client is connected.

`/checks` lists up to 40 fixed HTTP/TCP/DNS states for approved private chats. It uses the first eight characters of each check ID and does not send editable check names, URLs, hosts, ports, expected DNS addresses, or DNS answers. For the full history and target settings, use the panel.

The Web admin can probe optional Amnezia AWG2 control, inspect a read-only settings preview, and manage only SovaGrid-owned clients through `POST /api/v1/servers/{id}/amnezia/actions`. This uses a separate root broker that a local root administrator must enroll, install, and arm explicitly; the normal Hub and Agent deployment leaves it dormant. A successful broker `status` job unlocks the preview and mutation requests for 90 seconds, while the broker itself rechecks its root-owned enable marker on every transaction. New profiles and exports return ciphertext sealed to a browser-generated P-256 key, never plaintext in Hub. The API cannot enroll, arm, recover, edit arbitrary settings, change the AWG port or keys, update settings while clients exist, or touch non-SovaGrid-owned clients. For zero-client AWG3 numeric changes, an admin must review a pinned plan, request a five-minute confirmation handle and apply it once; the root broker rechecks every pin and verifies runtime after the journaled change. See [API.md](API.md).

Telegram is a cloud messaging channel. Commands and `/result` output sent through Telegram may contain sensitive data; do not put passwords or private keys in commands. The two-step confirmation prevents accidental execution, but cannot protect a compromised Telegram account. The agent runs ordinary commands with `/bin/sh -c` as its dedicated, unprivileged OS user, with a 15-second timeout and 8 KiB output cap. It never receives a root or sudo privilege from Hub.

When a Telegram admin binding is removed or changed to `viewer`/`operator`, Hub deletes that binding's pending confirmations and cancels its queued jobs in the same database transaction. Already delivered jobs cannot be recalled from an agent, and their results may still arrive. Review running work before changing roles.

## Commands from the admin panel

The Hub admin can queue a command with `POST /api/v1/servers/{id}/jobs` and `{ "command": "…" }`. This requires the existing Hub server opt-in (`POST /api/v1/servers/{id}/commands` with `{ "enabled": true }`) and the separate local agent opt-in (`"allow_remote_commands": true` in `/etc/sovagrid/agent.json`, followed by agent restart). The local agent setting must be changed by an OS administrator; the web panel cannot turn it on remotely. Ordinary commands run as the agent's unprivileged OS user, with a fixed 15-second timeout and 8 KiB output cap. Use `GET /api/v1/jobs/{job_id}` to poll for completion.

The admin-only `POST /api/v1/servers/{id}/processes/snapshot` queues a read-only process page with optional PID cursor, 1–32 row limit and short-name filter. Poll the returned job with the same session. Agent reads only `/proc` short names and RSS, skips inaccessible tasks, and returns no command lines or environment. Hub validates the page and holds its output in a bounded five-minute memory cache, never in metric or job history. The next cursor lets the panel traverse the live table without one giant response. See [API.md](API.md).

Managed WireGuard actions use `POST /api/v1/servers/{id}/vpn/actions` with a required canonical UUID `Idempotency-Key`. The body has one of six exact schemas: `create` (name, port, subnet, endpoint), `activate` (name), `add-client` and `revoke-client` (name, client), `sealed-export` (name, client, browser P-256 public key, optional split/full route), or `remove` (name, matching confirm_name). A full-route export requires a separately armed SovaGrid IPv4 routing policy; an upstream firewall can still block traffic. Hub validates each field and queues a fixed invocation of `/usr/local/bin/sovagrid-vpn-ctl`; it does not accept paths, plaintext profile exports, or arbitrary CLI text through this route. The Agent verifies this exact form and starts the client directly, without a shell. For `sealed-export` it forwards only a validated ciphertext envelope, replacing any malformed or failed broker output with a fixed error. The dedicated local VPN broker controls root-only operations without giving the Agent sudo. Exact broker commands have a 105-second job timeout and an 8 KiB output cap. Poll the returned job ID, then refresh the VPN inventory. See [API.md](API.md) for request and response fields.

Only an authenticated Hub admin bearer token may submit or read web jobs. Tokens are never sent as browser cookies. Audit records include the command hash and job transitions, but omit command text. The command text and any output remain in the protected SQLite database and may contain secrets, so avoid placing passwords or keys in commands. Queued web jobs are cancelled on admin logout, session expiry, or password change; delivered jobs may still complete. See [API.md](API.md) for exact fields and limits.

## Read-only systemd journals

The Web **Логи** section reads only service units that an online Agent advertises from its separately enabled local `journal_units` list. It requires the usual Hub command switch and admin login, then asks for confirmation. The optional five-minute auto-refresh requests at most one new snapshot every 30 seconds; Hub independently limits new journal jobs to one per 20 seconds per admin session and server while allowing idempotent replay. Snapshots replace earlier text and may omit entries during rotation or high log volume. For this action, Hub keeps at most 32 bounded outputs in memory for five minutes and returns each only to the requesting admin session; SQLite stores no log text. Logout, password change, or Hub restart clears it sooner. An independently installed, read-only `sovagrid-journal` broker has the journal OS group and enforces a second root-owned exact unit allowlist. The Agent's `sovagrid` user must not belong to `systemd-journal` or `adm`; general jobs keep their narrower OS access. General command admins can still speak the broker socket under the `sovagrid` UID for allowed units, and output from such a command goes into ordinary persistent job history. See [API.md](API.md) and the [Agent README](../sovagrid-agent/README.md#read-only-systemd-journal-in-web).

## Interactive browser terminal

The browser terminal is an explicit local Agent opt-in in addition to the Hub's `remote_commands_enabled` switch. Set both `allow_remote_commands=true` and `allow_interactive_terminal=true` in the Agent configuration and install its root-owned PTY broker; the [Agent README](../sovagrid-agent/README.md) and [deployment guide](../sovagrid-blueprint/DEPLOY.md) describe the installation. A terminal runs as the separate `sovagrid-shell` Unix user. It cannot use the Agent's local token or gain root privileges through this API. For server administration requiring root, use your existing SSH access.

The Agent initiates every HTTPS connection to the Hub; no Agent port is published. Hub relays input, resize events, and output in memory using bounded HTTP long polls. Only the Hub admin bearer session that created a terminal can read or send its frames. Logout, session expiry, password change, Agent token rotation, command disablement, idle timeout, and lifetime limit close it. Terminal bytes are not persisted to SQLite, audit records, Telegram, or job results. Hub restart loses active terminals. See [API.md](API.md) for the exact routes, sequence numbers, frame limits, and response codes.

## Operational limits of this first version

The remote-Agent feature wizard uses a separate administrator-only command-gate API. It verifies the active enrollment ID and its credential digest, then changes the gate only when the expected management revision still matches. The original Web command switch shares the same revision counter, so the wizard detects concurrent edits. This API does not install a PTY broker or change an Agent's local opt-ins; those operations still require the wizard's separately verified SSH step. Disabling the gate cancels queued commands and closes that server's terminal/file relays. See [API.md](API.md) for the bounded server picker and exact contract.

- Metrics: CPU, available memory, root filesystem, network byte counters, load, and uptime, plus bounded `details` with swap, mounted filesystems and inodes, individual interfaces, load5/load15, process counts, block-device I/O, selected systemd service states, PSI resource pressure, and CPU I/O wait/steal shares. PSI and CPU time details are sent only after the Hub advertises support in an accepted metric response. The latest online server summary also shows up to ten processes by RSS; this transient list stays in Hub memory and is never added to SQLite history. See [API.md](API.md) for the exact schema and limits. Existing SQLite databases gain the other detailed column and monitoring-settings table automatically on `serve`. Threshold alerts default to 90% CPU, memory, or root disk; a failed systemd service also raises an incident when the service inventory is available. Offline defaults to 120 seconds after the last received sample; sustained-problem delay defaults to zero. Change those established rules in the Web panel. Optional PSI, CPU iowait/steal, and root-filesystem inode alert rules have separate APIs, are disabled by default, and require at least two high samples separated by a configurable hold; the Web settings view for root inodes is still in development. Missing or inconsistent inode counters never claim recovery. `serve --cpu-threshold`, `--memory-threshold`, `--disk-threshold`, and `--offline-seconds` set initial defaults until a panel save.
- Raw metrics older than 30 days are pruned daily; tune with `serve --retention-days`. SQLite and a single Hub process suit a small personal installation; this is not a horizontally scalable time-series backend.
- Incident firing, recovery, and maintenance reminders use a durable SQLite outbox per approved private chat. Rows are committed with the incident change and survive a Hub restart or temporarily missing bot token; transient Telegram errors retry after 5 seconds up to a one-hour exponential backoff. An explicit Telegram flood-control delay is a minimum wait and is respected even when it exceeds one hour; that wait also survives a Hub restart. Within one incident and chat, recovery waits for the firing alert. Binding removal cancels pending messages, and maintenance suppresses stale alerts. Telegram can accept a message while its HTTP response is lost, so retry may send a duplicate: this is at-least-once delivery, not exactly-once. Invalid or blocked-chat responses (400/403/410) are dropped; token failures (401/404) keep retrying until the token is replaced. Command results and pairing replies still use a bounded in-memory queue; no token, command text, key, or journal content enters the incident outbox.
- A command job is delivered at most once. If an agent crashes after fetching it, the job can remain `delivered`; the Hub does not automatically repeat a potentially non-idempotent command.
- Hub accounts support viewer, operator, and administrator roles. Manage accounts in **Web → Настройки → Пользователи**: viewers read monitoring and VPN inventory; operators also acknowledge incidents; administrators manage commands, files, terminals, settings, Telegram, and users. Role changes, disabling/deleting an account, and password resets revoke only that account's sessions and queued work. A revision check prevents overwriting another administrator's edit; the last enabled administrator cannot be demoted, disabled, or deleted. Existing singleton admin credentials and sessions migrate atomically. Telegram bindings remain separate identities.
- Interactive browser terminals run as `sovagrid-shell` and require the separate local PTY broker. They are one per server and four per Hub process; they are not a replacement for privileged SSH access.

## Hub data snapshots on the Blueprint host

The root-only `sovagrid_hub.backup` tool creates an internally consistent SQLite snapshot while Hub is running in WAL mode. It also includes the current managed Telegram token, or the legacy external token, when one is configured. Run it from the **host** checkout installed by `sovagrid-blueprint/run.sh`:

```sh
cd /path/to/sovagrid-hub
sudo python3 -m sovagrid_hub.backup create
sudo python3 -m sovagrid_hub.backup list
sudo python3 -m sovagrid_hub.backup verify SNAPSHOT_UUID
```

Snapshots are kept in `/var/lib/sovagrid/backups/<UUID>` as root-owned directories (`0700`) with root-owned files (`0600`). A 4 GiB SQLite limit, 180-second snapshot deadline, free-space check and 1,000-snapshot count limit bound each operation; snapshots are **not** rotated or exported. `list` enumerates IDs; use `verify` to check a particular snapshot's exact file set, SHA-256 digests, SQLite integrity and Telegram token relationship. The snapshot can contain passwords' hashes, sessions, command output and the **plaintext bot token**. Keep it root-private and protect any external copy accordingly. The tool emits fixed error codes and metadata, never tokens or database rows.

Blueprint can also install a root-owned, socket-activated backup broker for the Web **Резервные копии** panel. The Hub container sees only `/run/sovagrid-hub-backup/control.sock`; it never mounts `/var/lib/sovagrid/backups`. An unrestricted Hub administrator can list snapshot IDs, verify one, or create one with an idempotency key. A verified response contains only the UUID, UTC creation time, database size, and whether it included a Telegram token. A lost creation response should be resolved by refreshing the list and verifying new IDs; a deliberate retry must reuse the same key. Creation uses the same host lock as updates and offline restore, requires extra free-space headroom, and limits new snapshots to one per five minutes. There is no automatic schedule. The panel cannot download or delete a snapshot. A confirmed Web restore also uses this broker, with a durable request UUID, disk preflight before stopping Hub, and status/history routes after reconnecting. Web recovery requires a running Hub; if it stays stopped, use Connect/root SSH. See the [API contract](API.md#hub-backup-control) and [Blueprint deployment guide](../sovagrid-blueprint/DEPLOY.md) for the host service.

This is a **Hub-state backup only**, not a complete SovaGrid host backup. It does not include Caddy's private CA, `/etc/sovagrid` Agent credentials/configuration, VPN keys or profiles, other root brokers' configuration, or arbitrary application files. The tool supports only the exact Blueprint `/var/lib/sovagrid` layout and UID/GID 10001, not the standalone systemd layout described above.

An offline restore is available to the root-only host CLI. Stop the Blueprint Hub container first and keep it stopped through `plan-restore`, `apply-restore`, and any immediate `undo-restore`. The tool verifies Docker's Compose `sovagrid/hub` container state, takes the same candidate lock as both Blueprint update workers, validates the target and a new safety snapshot, and binds the plan to the exact current database, WAL, SHM and managed-token inodes and hashes. It refuses a changed source, unknown file, symlink, hardlink, directory mountpoint or legacy external token. The external token lives outside the Hub data directory and cannot be atomically exchanged with SQLite. A snapshot with a managed Telegram token can be restored only while the current Hub uses **that same token**; a different token needs a separately designed resynchronization flow, so the tool fails closed. A snapshot without a token disables the bot. Do not replace a live `hub.sqlite` manually.

For GUI clients with root SSH, `sovagrid_hub.backup_restore` coordinates the normal offline restore in one command. It accepts `apply SNAPSHOT_UUID REQUEST_UUID`, `status REQUEST_UUID`, `list`, and an explicitly confirmed `recover REQUEST_UUID`; the UUID request key must be generated once before confirmation and reused after a lost SSH response. `apply` stops only the unique Compose `sovagrid/hub` container whose `/data` bind points at `/var/lib/sovagrid/hub`, creates a safety snapshot and plan, exchanges the data, starts the same container, checks Docker health and the exact `/data` directory inode from inside the container, and finalizes the retained old directory. It holds the candidate update lock across the whole operation. The command returns one bounded JSON object with `ok`, `protocol`, `request_id`, `target_id`, `phase`, `safety_id`, `plan_id`, `hub_running`, `error`, and `created_at`; `list` returns up to 100 newest entries in `restores`, always retaining unfinished entries. Journal files stay root-only in `/var/lib/sovagrid/backups` so the GUI can rediscover a result after closing.

The orchestrator attempts an exact offline undo if start or health fails. If the restored database changed while Hub was starting, the existing undo safety check refuses the swap; the journal then says `recovery_required`, Hub remains stopped, and the safety snapshot, plan and retained directory remain available. `status` and `list` are read-only. The explicit `recover` action holds the same lock, rechecks the exact container and old/new data fingerprints, and restarts the original data or completes a checked restored state. If Hub wrote to the restored database before interruption, `recover` first makes another validated safety snapshot. Unknown or tampered state remains offline with `recovery_required`; the GUI must show that state and must not retry an exchange blindly. Repeating an incomplete `apply` reports its recorded state without starting another restore. A completed `apply` or `recover` can be replayed with the same key and returns its recorded result. Existing manual `plan-restore`/`apply-restore`/`undo-restore`/`finalize-restore` commands remain for guided recovery.

```sh
sudo python3 -m sovagrid_hub.backup plan-restore SNAPSHOT_UUID
sudo python3 -m sovagrid_hub.backup apply-restore PLAN_UUID
# If the new state should be reverted before Hub restarts:
sudo python3 -m sovagrid_hub.backup undo-restore PLAN_UUID
# Otherwise, restart Hub and confirm health and sign-in, then remove retained old files:
sudo python3 -m sovagrid_hub.backup finalize-restore PLAN_UUID
```

`apply-restore` removes restored login sessions and one-time SSH grants, cancels queued jobs and Telegram command confirmations, marks delivered jobs as uncertain, drops old unsent incident notifications and pending bot pairing requests, and invalidates old successful service/Amnezia status jobs. This prevents backed-up work from running again or authorizing a fresh broker action from stale status. With an unchanged Telegram token, it carries forward the higher update cursor from the current safety snapshot and refreshes its timestamp to avoid replay after the cursor's idle expiry. The restored database still contains historical accounts, server roles, Agent credentials and access policies: review users, Agent tokens and permissions after sign-in. A restored Agent with a rotated live token may need re-enrollment.

The tool uses Linux `renameat2(RENAME_EXCHANGE)` to swap the complete data directory in one filesystem operation. It leaves the old directory root-inaccessible at `/var/lib/sovagrid/.restore-PLAN_UUID` and leaves Hub stopped; it never restarts the container. `undo-restore` exchanges the directories back only while the restored state and retained old state are unchanged. Once Hub writes to the restored database, undo may refuse; create a new offline plan targeting the safety snapshot instead. `finalize-restore` deletes the retained old directory and review record after an independently confirmed restart; the safety snapshot remains. A crash after exchange can leave the plan and old directory in place: inspect both before starting Hub, then use `undo-restore` or `finalize-restore` as appropriate. These commands are an internal recovery contract for a future graphical flow; they do not stop/start Hub or restore the other host resources listed above.

## Reviewed external Agent update

On a Hub-only host with an Agent still enrolled with another Hub, an unrestricted admin can inspect `GET /api/v1/external-agent-update` and submit read-only `POST /api/v1/external-agent-update/{preview,preflight}` with the staged archive SHA-256 and current Hub manifest SHA-256. Preflight returns a review SHA-256 and a bounded list of source changes; it does not reserve an Agent idle ACK. The archive must already be staged by the separate host installer. The Hub cannot fetch it through this API.

Confirmed `POST /api/v1/external-agent-update/apply` takes a client-generated UUID, all four exact SHA-256 values, and `confirmed:true`. The root backup broker writes a durable root-only request, then starts only the fixed `sovagrid-external-agent-apply@<UUID>.service`; it never performs the Agent tree exchange in its own sandbox. Reusing the same UUID with changed hashes returns a conflict, and no response loss triggers an automatic restart. `GET /api/v1/external-agent-update/operations/<UUID>` and the bounded `GET /api/v1/external-agent-update/operations` list allow the panel to recover a result after reconnecting. An accepted or running operation whose unit is inactive/failed becomes `uncertain` and needs administrator review. The UI must not repeat apply automatically. Every mutation requires unrestricted admin and same-origin browser access; apply requests are audited before dispatch. The dedicated Blueprint unit and Agent idle protocol must be installed before apply can start.
